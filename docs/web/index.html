1

Qué es tasks-ai

Un gestor de tareas para el proyecto en el que estás, no un servicio al que te conectas. No hay servidor que mantener ni cuenta que crear: hay un binario y una carpeta.

Las tareas viven en .tasks-ai/tasks.db, dentro del propio proyecto, y se usan de dos maneras con el mismo binario: por línea de órdenes, siempre en JSON, y por una interfaz web que el binario sirve cuando se le pide con serve. Las dos superficies hacen exactamente las mismas operaciones sobre los mismos datos, así que mover el proyecto de carpeta o de máquina no se lleva nada por delante salvo que olvides la carpeta .tasks-ai/.

RutaQué es
.tasks-ai/tasks.dbLa base con las tareas, los bloqueos, los comentarios, las etiquetas y los ADR.
.tasks-ai/settings.jsonEl prefijo de las referencias, la base, la dirección y el puerto de la interfaz, y el nivel de registro.
.tasks-ai/AGENTS.mdLas instrucciones para quien trabaja el proyecto, persona o agente.
tasks-aiEl binario. No necesita nada más para funcionar: la interfaz web viaja dentro.

El recorrido completo, en cuatro pasos

initInstala

Deja la carpeta del producto con la base, los ajustes, las instrucciones, el contrato de etiquetas y las dos extensiones de agente, y un proyecto ya no lo acepta dos veces.

createRegistra

Cada tarea entra con título obligatorio y, si quieres, descripción, prioridad, responsable, notas y padre.

listConsulta

El listado devuelve todas las tareas, también las cerradas, con su estado y si están bloqueadas.

serveMira

La misma base, en el navegador, con árbol, filtros y avisos de los cambios hechos desde otra ventana.

La regla mental. Una tarea es una fila con identidad estable; su referencia visible —tk-1— es lo que escribes y lo que se ve. La base es un archivo, y por eso no hay nada que arrancar antes de trabajar.

2

Empezar en un proyecto

Compilar es el único paso que necesita Go. A partir de ahí, todo lo hace el binario.

go build ./cmd/tasks-ai      # deja el binario tasks-ai en la carpeta actual
./tasks-ai init              # instala el producto en el proyecto en el que estés
go build ./cmd/tasks-ai      # leaves the tasks-ai binary in the current folder
./tasks-ai init              # installs the product in the project you are in

En Windows el binario se llama tasks-ai.exe: go build lo deja con ese nombre, init lo copia a .tasks-ai\bin\tasks-ai.exe y las dos extensiones buscan ese mismo archivo. Las órdenes de esta página se escriben con ./tasks-ai; en PowerShell, .\tasks-ai.exe —y .\tasks-ai.exe init para instalar—.

init busca hacia arriba la raíz del proyecto y deja ahí la carpeta .tasks-ai/. Responde en JSON con lo que dejó: la carpeta, la base, las instrucciones, el prefijo, el texto que hay que añadir fuera para que las personas y los agentes encuentren las instrucciones, el binario instalado, la extensión de Pi, el plugin de OpenCode y el contrato de etiquetas. Con --prefix el prefijo de las referencias se fija en la propia instalación, en vez de tk, y las instrucciones que deja lo usan en sus ejemplos.

3

El modelo de datos

Siete cosas: tareas, etiquetas, asignaciones de etiquetas, dependencias, comentarios, decisiones y los ajustes de la base. Todo lo demás es presentación.

La tarea

CampoTipoQué significa
identeroIdentidad interna. No se presenta: sirve para que renombrar o cambiar el prefijo no rompa nada.
reftextoLa referencia visible, compuesta con el prefijo del proyecto: tk-1.
titletextoObligatorio.
descriptiontextoOpcional.
statusenumeradoopen, in_progress o done.
blockedbooleanoCalculado: cierto mientras alguna bloqueante no esté cerrada. No se guarda.
priorityenteroDe 0 a 3, con 2 por omisión. Fuera de rango se rechaza.
assigneetextoOpcional. Es texto libre, no un usuario del sistema.
parent_identeroEl número interno del padre. La referencia del padre se compone con el prefijo.
created_at, updated_atfechaEn UTC. Cambian solos.
close_reasonenumeradoEl motivo del cierre, o nulo si la tarea no está cerrada.
notestextoEl plan del trabajo: es un solo texto y se sobrescribe.

La prioridad no tiene más significado que su orden. El producto valida el rango y nada más: no la ordena, no la interpreta y no cambia el comportamiento de ninguna orden. Lo que signifique 0 lo decides tú y lo escribes en las reglas del proyecto.

El texto no guarda el estado. El título, la descripción, las notas y el cuerpo de un comentario no dicen en qué punto está el trabajo ni qué queda por entregar: el estado lo dicen la tarea y sus bloqueos, y Git lo que se entregó. El producto lo comprueba antes de escribir y rechaza el texto que nombra un hash de commit, una rama o una referencia a un remoto, o que declara el estado de la tarea o de la entrega con la forma que reconoce; el rechazo no guarda nada y nombra el campo y el fragmento. Entrecomillar no exime: un texto que cita la frase prohibida se rechaza igual.

La etiqueta

El catálogo es del proyecto, no de cada tarea: una etiqueta tiene nombre, color y descripción, y las tareas la llevan por su número interno. Por eso renombrar una etiqueta no toca ninguna tarea, y borrarla deja a sus tareas sin ella.

  • El nombre es único y se compara tal cual: docs y Docs son dos etiquetas distintas.
  • El color es uno de la paleta y por omisión es blue.
  • El uso de una etiqueta sale de las asignaciones, así que tags sabe cuántas tareas la llevan.

La dependencia

Una dependencia dice que una tarea espera a otra: mientras la segunda no esté cerrada, la primera aparece bloqueada. No hay estado «bloqueada» guardado, así que quitar el bloqueo devuelve la tarea a su estado real sin tocar nada más. Bloquear la misma pareja dos veces no cambia nada, y retirar un bloqueo que no está tampoco.

El comentario

Un comentario es identidad, cuerpo y fecha. El cuerpo se puede editar: la identidad con la que se añadió y su fecha de creación se quedan como estaban. Se leen del primero al último. Es el sitio para las decisiones y las evidencias; las notas son el sitio para el plan.

La decisión

Un ADR guarda una decisión con su contexto y sus consecuencias: número correlativo, referencia ADR-NNN, slug inmutable, título, estado, fecha y quiénes deciden. El estado es proposed, accepted, rejected, deprecated o superseded. El cuerpo —contexto, decisión, consecuencias y alternativas— se congela al salir de proposed: después solo se admiten cambios de estado y añadidos fechados en «Más información». No hay borrado, y un cambio de decisión se publica como un ADR nuevo que sustituye al anterior.

4

Las órdenes

Todas responden en JSON. Los errores también son JSON, con un objeto error, y la salida distingue dos casos: 2 cuando el uso o la entrada no son válidos, y 1 en cualquier otro rechazo.

init— instala el producto en el proyecto

Deja .tasks-ai/ con el catálogo de etiquetas puesto —los ocho tipos y ODD, epic y task, cada una con su descripción— y el contrato en .tasks-ai/CONTRATO_ETIQUETAS.md, y devuelve lo que dejó. Con --prefix el prefijo de las referencias se fija al instalar, y pedir uno distinto del que ya tienen los ajustes se rechaza. No es repetible: un proyecto ya instalado lo rechaza, y una instalación a medias se completa sin borrar nada, respetando las etiquetas que ya existan. Un árbol que traiga un enlace simbólico dentro de .tasks-ai/ se rechaza: el producto no escribe a través de un enlace.

./tasks-ai init
# { "dir": "...", "db": "...", "instructions": "...", "prefix": "tk", "pointer": "...",
#   "binary": "...", "extension": "...", "opencode": "...", "contract": "..." }

./tasks-ai tags                # el catálogo con el que nace el proyecto
# [ { "name": "feat", "color": "blue", "description": "Capacidad o integración nueva" }, ... ]

./tasks-ai init --prefix tai   # fija el prefijo de las referencias al instalar
# { "dir": "...", "db": "...", "instructions": "...", "prefix": "tai", "pointer": "..." }

./tasks-ai init      # segunda vez sobre el mismo proyecto
# { "error": "the project already has the product installed in /home/ana/informes/.tasks-ai" }   salida 1
./tasks-ai init
# { "dir": "...", "db": "...", "instructions": "...", "prefix": "tk", "pointer": "...",
#   "binary": "...", "extension": "...", "opencode": "...", "contract": "..." }

./tasks-ai tags                # the catalogue the project is born with
# [ { "name": "feat", "color": "blue", "description": "Capacidad o integración nueva" }, ... ]

./tasks-ai init --prefix tai   # fixes the prefix of the references at install time
# { "dir": "...", "db": "...", "instructions": "...", "prefix": "tai", "pointer": "..." }

./tasks-ai init      # second time on the same project
# { "error": "the project already has the product installed in /home/ana/reports/.tasks-ai" }   exit 1

create— crea una tarea o una subtarea

El título es obligatorio. Con --parent la tarea nace como subtarea de la que se le da, y con --tags nace con sus etiquetas, separadas por comas.

OpciónQué hace
-t, --titleTítulo. Obligatorio.
-d, --descriptionDescripción.
--notesNotas: el plan del trabajo.
--priorityEntero de 0 a 3. Por omisión 2.
--assigneePersona responsable.
--parentReferencia del padre: la tarea nace como subtarea.
--tagsEtiquetas con las que nace, separadas por comas. Una que no esté en el catálogo se rechaza y no deja la tarea escrita.
 
./tasks-ai create --title "Revisar el tono del resumen" --parent tk-1 --priority 3
# devuelve la tarea con "parent_id": 1

./tasks-ai create --title "Arreglar el recuento" --tags "fix,ODD"
# devuelve la tarea con "tags": ["ODD", "fix"]

./tasks-ai create --title "Probar" --priority 9
# { "error": "priority 9 is outside the range 0-3" }   salida 2
./tasks-ai create --title "Review the summary's tone" --parent tk-1 --priority 3
# returns the task with "parent_id": 1

./tasks-ai create --title "Fix the counter" --tags "fix,ODD"
# returns the task with "tags": ["ODD", "fix"]

./tasks-ai create --title "Test" --priority 9
# { "error": "priority 9 is outside the range 0-3" }   exit 2

list— todas las tareas del proyecto

Devuelve el listado entero, las cerradas incluidas, cada una con su referencia, su estado, su título y si está bloqueada. No hay filtros ni paginación: el listado es el proyecto.

./tasks-ai list
# [ { "id": 1, "ref": "tk-1", "title": "...", "status": "open", "blocked": true, ... },
#   { "id": 2, "ref": "tk-2", "title": "...", "status": "done", "blocked": false, ... } ]

show— una tarea con lo que la rodea

Es la única orden que trae el contexto: las hijas, las bloqueantes, los dependientes y los comentarios. Para saber por qué una tarea está bloqueada, o qué espera a qué, se mira aquí.

./tasks-ai show tk-1
# { "id": 1, "ref": "tk-1", ..., "children": [ ... ], "blockers": [ ... ],
#   "dependents": [], "comments": [ { "id": 1, "body": "...", "created_at": "..." } ] }

./tasks-ai show tk-99
# { "error": "there is no task with reference \"tk-99\"" }   salida 1
./tasks-ai show tk-1
# { "id": 1, "ref": "tk-1", ..., "children": [ ... ], "blockers": [ ... ],
#   "dependents": [], "comments": [ { "id": 1, "body": "...", "created_at": "..." } ] }

./tasks-ai show tk-99
# { "error": "there is no task with reference \"tk-99\"" }   exit 1

update— cambia lo que se pide y nada más

Un campo que no se menciona no cambia; un texto que se da vacío deja ese campo sin valor. El estado va solo por aquí, y solo open o in_progress: cerrar tiene su propia orden, con su motivo.

OpciónQué hace
-t, --titleNuevo título.
-d, --descriptionNueva descripción; vacía la quita.
--notesNuevas notas; vacías las quitan.
--priorityNueva prioridad, de 0 a 3.
--assigneeNuevo responsable; vacío lo quita.
--tagsLa lista entera de etiquetas, separadas por comas; vacía las quita todas.
--statusin_progress pone en curso y solo cabe desde open; open devuelve a pendiente.
--parentLa referencia del nuevo padre: la asigna o la mueve; vacía deja la tarea sin padre. Un ciclo se rechaza sin escribir nada.
 
./tasks-ai update --status in_progress tk-2      # en curso
./tasks-ai update --tags "docs,fix" tk-1         # toda la lista de etiquetas
./tasks-ai update --assignee "" tk-2             # le quita el responsable
./tasks-ai update --parent tk-1 tk-3             # la cuelga de tk-1; --parent "" la deja en su nivel

./tasks-ai update --status done tk-1
# { "error": "status \"done\" is not set here: closing goes through close, with its reason" }   salida 2
./tasks-ai update --status in_progress tk-2      # in progress
./tasks-ai update --tags "docs,fix" tk-1         # the whole tag list
./tasks-ai update --assignee "" tk-2             # clears the assignee
./tasks-ai update --parent tk-1 tk-3             # hangs it under tk-1; --parent "" leaves it on its own

./tasks-ai update --status done tk-1
# { "error": "status \"done\" is not set here: closing goes through close, with its reason" }   exit 2

close— cierra con motivo

El motivo es obligatorio y es uno de los cinco conocidos; cerrar deja el estado en done y guarda el motivo.

MotivoCuándo
doneSe hizo lo que la tarea pedía.
duplicateYa hay otra tarea que la cubre.
absorbedSu contenido pasó a otra tarea.
staleDejó de tener sentido.
supersededOtra tarea la sustituye.
 
./tasks-ai close --reason done tk-2
# { ..., "status": "done", "close_reason": "done" }

./tasks-ai close tk-1
# { "error": "the close reason is missing: use --reason with one of done, duplicate, absorbed, stale, superseded" }   salida 2
./tasks-ai close --reason done tk-2
# { ..., "status": "done", "close_reason": "done" }

./tasks-ai close tk-1
# { "error": "the close reason is missing: use --reason with one of done, duplicate, absorbed, stale, superseded" }   exit 2

reopen— devuelve una cerrada a pendiente

Quita el motivo de cierre y deja el estado en open. Reabrir algo que no está cerrado se rechaza, y no hay más vuelta atrás que volver a cerrarla.

./tasks-ai reopen tk-2
./tasks-ai reopen tk-1
# { "error": "cannot reopen task \"tk-1\": it is not closed" }   salida 1
./tasks-ai reopen tk-2
./tasks-ai reopen tk-1
# { "error": "cannot reopen task \"tk-1\": it is not closed" }   exit 1

block y unblock— dependencias entre tareas

block deja la primera bloqueada por la segunda; unblock retira ese bloqueo. Las dos devuelven la primera tarea tal como queda. Una tarea no puede bloquearse por sí misma, y los ciclos se permiten: el producto no impide que A espere a B y B a A.

./tasks-ai block tk-1 tk-2      # tk-1 espera a tk-2
./tasks-ai unblock tk-1 tk-2    # deja de esperar

./tasks-ai block tk-1 tk-1
# { "error": "task \"tk-1\" cannot be blocked by itself" }   salida 2
./tasks-ai block tk-1 tk-2      # tk-1 waits for tk-2
./tasks-ai unblock tk-1 tk-2    # stops waiting

./tasks-ai block tk-1 tk-1
# { "error": "task \"tk-1\" cannot be blocked by itself" }   exit 2

comment comment list comment edit— el histórico de la tarea

El cuerpo es obligatorio. Cada comentario tiene su identidad y su fecha: comment añade uno y devuelve la tarea tal como está, comment list devuelve los de la tarea del primero al último, y comment edit <referencia> <id> cambia el cuerpo de uno conservando su identidad y su fecha. El id se entiende dentro de la tarea: un número que no es de sus comentarios se rechaza como una referencia que no resuelve.

./tasks-ai comment --body "Decidido: el informe se entrega el viernes." tk-1
./tasks-ai comment list tk-1
# [ { "id": 1, "body": "Decidido: el informe se entrega el viernes.", "created_at": "..." } ]

./tasks-ai comment edit tk-1 1 --body "Decidido: el informe se entrega el lunes."
# la tarea, con el cuerpo cambiado y la misma identidad y fecha en el comentario
./tasks-ai comment --body "Decided: the report ships on Friday." tk-1
./tasks-ai comment list tk-1
# [ { "id": 1, "body": "Decided: the report ships on Friday.", "created_at": "..." } ]

./tasks-ai comment edit tk-1 1 --body "Decided: the report ships on Monday."
# the task, with the body changed and the same identity and timestamp on the comment

tags— el catálogo con su uso

Devuelve todas las etiquetas ordenadas por nombre: identidad, nombre, color, descripción y número de tareas que la llevan.

./tasks-ai tags
# [ { "id": 3, "name": "docs", "color": "blue",
#     "description": "Documentación, ADR, contrato o informe", "uses": 1 }, ... ]
./tasks-ai tags
# [ { "id": 3, "name": "docs", "color": "blue",
#     "description": "Documentation, ADR, contract or report", "uses": 1 }, ... ]

tag create tag edit tag delete— el catálogo se cambia por nombre

Las etiquetas viajan por su nombre y las tareas las guardan por su número interno. tag edit cambia solo lo que se pide, y renombrar no toca ninguna tarea.

OrdenOpciones
tag create--name obligatorio; --color —blue, purple, green, yellow, orange, red—; --description
tag edit <nombre>--name, --color, --description: solo lo que se pide
tag delete <nombre>Sin opciones: borra la etiqueta y sus asignaciones
 
./tasks-ai tag create --name "revision" --color blue --description "Revisión de textos"
./tasks-ai tag edit --color green revision
./tasks-ai tag delete revision
# warning: the tag "revision" was used by the tasks tk-1; their assignments have been deleted
# { "id": 12, "name": "revision", "color": "green", "description": "..." }
./tasks-ai tag create --name "revision" --color blue --description "Text review"
./tasks-ai tag edit --color green revision
./tasks-ai tag delete revision
# warning: the tag "revision" was used by the tasks tk-1; their assignments have been deleted
# { "id": 12, "name": "revision", "color": "green", "description": "..." }

El aviso de tag delete va por la salida de errores, no por el JSON: si algo dependía de esa etiqueta, se entera quien esté mirando la terminal. Una etiqueta sin uso se borra sin aviso.

serve— la interfaz y la API del producto

Arranca la interfaz web y la API en la dirección y el puerto de los ajustes, y anuncia los cambios por un canal abierto para que dos sesiones se vean. Lo que escribe va por la salida de errores.

./tasks-ai serve
# time=... level=INFO msg="listening on http://127.0.0.1:8890"

La raíz redirige a la interfaz y la API conserva sus rutas /api/...; el detalle está en la sección 7 y en la 8.

completion— el autocompletado de la shell

La orden que añade pflag a cualquier binario: genera el guion de autocompletado para la shell que se le pida. No toca las tareas.

./tasks-ai completion bash      # también zsh, fish y powershell
./tasks-ai completion bash      # also zsh, fish and powershell

adr— las decisiones durables del proyecto

Un ADR guarda una decisión con su contexto y sus consecuencias. Vive en la misma base que las tareas y se escribe con el producto; docs/decisions/ es una exportación generada, versionada para que Git guarde la revisión de cada decisión.

./tasks-ai adr create --title "Adoptar SQLite" --deciders "Ana"   # ADR-001, en proposed
./tasks-ai adr edit 1 --decision "Se usa SQLite como única base."  # el cuerpo se escribe mientras sigue en proposed
./tasks-ai adr edit 1 --status accepted                            # aceptarla congela el cuerpo
./tasks-ai adr edit 1 --note "Se comprobó en producción"           # solo «más información» admite añadidos
./tasks-ai adr edit 1 --status superseded --superseded-by 2        # ADR-002 la sustituye
./tasks-ai adr list                                                # los ADR con su contexto
./tasks-ai adr show ADR-001                                        # uno entero, con sus secciones
./tasks-ai adr import --dir docs/decisions                         # guarda los ADR que aún no están
./tasks-ai adr export --dir docs/decisions                         # escribe la exportación y su índice
./tasks-ai adr export --dir docs/decisions --check                 # sale con 1 si hay deriva
./tasks-ai adr create --title "Adopt SQLite" --deciders "Ana"   # ADR-001, in proposed
./tasks-ai adr edit 1 --decision "SQLite is the only database."  # the body is written while it stays proposed
./tasks-ai adr edit 1 --status accepted                          # accepting it freezes the body
./tasks-ai adr edit 1 --note "Checked in production"             # only more information takes additions
./tasks-ai adr edit 1 --status superseded --superseded-by 2      # ADR-002 supersedes it
./tasks-ai adr list                                              # the ADRs with their context
./tasks-ai adr show ADR-001                                      # one whole, with its sections
./tasks-ai adr import --dir docs/decisions                       # stores the ADRs that are not there yet
./tasks-ai adr export --dir docs/decisions                       # writes the export and its index
./tasks-ai adr export --dir docs/decisions --check               # exits 1 when there is drift

El cuerpo —título, contexto, decisión, consecuencias y alternativas— se congela al salir de proposed: después solo se admiten añadidos fechados en «Más información», y un cambio de decisión se publica como un ADR nuevo que sustituye al anterior. No hay borrado. adr import --dir lee un directorio de archivos y guarda los ADR que aún no están, sin duplicarlos.

5

El ciclo de vida

Tres estados y dos reglas que se derivan. Saber cuáles son las transiciones legales evita la mitad de los errores.

openPendiente

Como nace una tarea. Es también donde vuelve reopen.

in_progressEn curso

Se entra desde pendiente con update --status in_progress; se sale a pendiente con --status open.

doneHecha

Solo se llega con close y su motivo. No se pone con update.

Las transiciones, una a una

DesdeOrdenQueda enQué pasa si no cabe
openupdate --status in_progressin_progress—
in_progressupdate --status openopen—
cualquiera salvo doneclose --reason ...doneSalida 1 si tiene subtareas abiertas.
donereopenopen, sin motivoSalida 1 si no estaba cerrada.
doneupdate --status in_progressSe rechazaSalida 2: para volver hay que reabrir.
cualquieraupdate --status doneSe rechazaSalida 2: cerrar va por close.

Las dos reglas que se calculan

Bloqueada. Una tarea está bloqueada mientras tenga alguna bloqueante sin cerrar. No es un estado que se guarde: se calcula en cada lectura, y por eso quitar el bloqueo la devuelve a lo que era sin tocar la base.

El cierre en cascada no existe. Cerrar una subtarea no cierra a su padre, y cerrar un padre con subtareas abiertas se rechaza sin escribir nada. Quien cierra decide qué cierra.

./tasks-ai close --reason done tk-1
# { "error": "cannot close task \"tk-1\": it has open subtasks" }   salida 1
./tasks-ai close --reason done tk-1
# { "error": "cannot close task \"tk-1\": it has open subtasks" }   exit 1

Notas y comentarios no son lo mismo. notes es un solo texto que se sobrescribe y guarda el plan —los pasos y lo que hay que tener presente al retomar la tarea—, no el estado: el estado lo dicen la propia tarea, sus bloqueos y Git. Los comentarios son el histórico de la tarea —cada uno con su identidad y su fecha, y con el cuerpo editable— y sirven para lo que no debe perderse: la petición, la decisión con su razón y la evidencia.

6

Recetas

Cinco formas de trabajar que el producto hace bien, con las órdenes en su orden.

Una épica con subtareas

La épica es una tarea normal; las subtareas se crean con --parent. El listado deja ver el padre en cada hija, y la interfaz las anida y muestra el progreso.

./tasks-ai create --title "Publicar la versión 2"                     # tk-3
./tasks-ai create --title "Actualizar las capturas" --parent tk-3     # tk-4
./tasks-ai create --title "Escribir las notas" --parent tk-3          # tk-5
./tasks-ai show tk-3      # las hijas, con su estado y su progreso
./tasks-ai create --title "Ship version 2"                        # tk-3
./tasks-ai create --title "Update the screenshots" --parent tk-3     # tk-4
./tasks-ai create --title "Write the release notes" --parent tk-3    # tk-5
./tasks-ai show tk-3      # the children, with their status and progress

Encadenar trabajo con dependencias

Cuando una tarea no se puede empezar hasta que otra esté cerrada, se bloquea. El bloqueo se resuelve solo al cerrar la bloqueante, sin quitar nada a mano.

./tasks-ai block tk-5 tk-4        # escribir las notas espera a las capturas
./tasks-ai list                   # tk-5 sale bloqueada mientras tk-4 siga abierta
./tasks-ai close --reason done tk-4
./tasks-ai list                   # tk-5 deja de estar bloqueada
./tasks-ai block tk-5 tk-4        # writing the notes waits for the screenshots
./tasks-ai list                   # tk-5 shows blocked while tk-4 is open
./tasks-ai close --reason done tk-4
./tasks-ai list                   # tk-5 is no longer blocked

Ordenar el trabajo con etiquetas

El catálogo nace con la instalación y se amplía cuando hace falta; las tareas lo llevan por nombre. Una etiqueta con color y descripción se lee mejor en la pantalla, y renombrarla no rompe ninguna tarea.

./tasks-ai tag create --name "urgente" --color red --description "Entrega de esta semana"
./tasks-ai update --tags "docs,urgente" tk-1
./tasks-ai tags                   # el uso de cada una
./tasks-ai tag create --name "urgent" --color red --description "Delivery this week"
./tasks-ai update --tags "docs,urgent" tk-1
./tasks-ai tags                   # how many tasks carry each one

Dejar constancia de una decisión

Lo que hay que poder releer meses después va en un comentario; el plan de la tarea va en las notas, que se pueden sustituir sin miedo.

./tasks-ai comment --body "Se descarta el PDF: el informe se entrega en HTML." tk-1
./tasks-ai update --notes "Revisar el tono de la introducción; después, el índice." tk-1
./tasks-ai comment --body "PDF is out: the report ships as HTML." tk-1
./tasks-ai update --notes "Review the tone of the introduction; then the index." tk-1

Trabajar con un agente

La carpeta del producto lleva sus propias instrucciones. El agente las encuentra si el proyecto las enlaza, y a partir de ahí usa las mismas órdenes que una persona: no hay una superficie distinta para él.

# en el archivo de instrucciones del proyecto
@.tasks-ai/AGENTS.md

# lo que el agente hace después, igual que una persona
./tasks-ai list
./tasks-ai update --status in_progress tk-2
./tasks-ai comment --body "Prueba añadida y en verde." tk-2
./tasks-ai close --reason done tk-2
# in the project's instruction file
@.tasks-ai/AGENTS.md

# what the agent does next, same as a person
./tasks-ai list
./tasks-ai update --status in_progress tk-2
./tasks-ai comment --body "Test added and green." tk-2
./tasks-ai close --reason done tk-2

Una tarea no pasa a ser «del agente» porque la escriba un agente. El responsable es texto libre: si quieres distinguir quién hizo qué, escríbelo con --assignee o déjalo en los comentarios. El producto no guarda un autor por operación.

7

La interfaz web

La misma base, en el navegador. No hay nada que construir ni que instalar: la interfaz viaja dentro del binario.

./tasks-ai serve
# time=2026-10-17T10:30:49+02:00 level=INFO msg="listening on http://127.0.0.1:8891"

La dirección y el puerto salen de settings.json. La raíz responde con una redirección a la interfaz —código 302—, así que abrir http://127.0.0.1:8890/ es suficiente.

curl -s -D - -o /dev/null http://127.0.0.1:8891/
# HTTP/1.1 302 Found
# Location: /task-manager/app-vue.html

Qué se ve

El árbol

Las tareas anidadas por su padre, cada épica con el progreso de sus subtareas y el recuento del proyecto.

Las pestañas

Pendientes, en curso y hechas, con el mismo estado que devuelve la API: lo que ves es lo que hay.

El detalle

La descripción, las notas y el cuerpo del comentario se dibujan con el formato que traigan —énfasis, listas, enlaces, tablas— y conservan sus saltos de línea. Lo que ejecuta o carga algo se descarta al dibujarlo: un texto pegado de fuera se lee, no se obedece.

Las decisiones

Una vista propia lista los ADR con su contexto, los busca en el servidor y los lee y edita en su tarjeta; el cuerpo se dibuja como markdown.

Los filtros

Por estado, prioridad, etiqueta y texto. El texto busca en el título, la referencia, las etiquetas, la descripción, las notas y los comentarios. Se combinan, y el árbol se pliega y se despliega.

Los avisos de cambio

Lo que cambia desde otra ventana o desde la terminal aparece solo, con su aviso, sin recargar.

Lo que conviene saber antes de fiarse de la pantalla

  • El plegado del árbol se guarda en el navegador. Con un filtro puesto, una tarea que encaja puede no verse porque su padre está plegado: despliega antes de dudar del dato, o compruébalo con show.
  • La ventana que hace un cambio no repite su propio aviso; las demás sí lo ven. El aviso no dice quién lo pidió, porque el estado y el aviso son los mismos venga de donde venga.
  • Al abrir o recargar la pantalla no aparece el historial de avisos anteriores: el canal cuenta lo que pasa mientras miras.

Dos sesiones se ven porque el aviso se lee de la base. No hay memoria compartida entre procesos: un cambio pedido por la terminal llega al canal igual que uno pedido por la API.

Visor de escritorio · opcional

El tablero, también en una ventana nativa

La interfaz siempre está disponible en el navegador. Si prefieres usarla como aplicación, tasks-viewer abre la misma pantalla en una ventana nativa: un webview ligero escrito en Go, no un navegador completo.

  • Antes de abrirlo, deja tasks-ai serve en marcha: el visor lee el tablero por la API.
  • La conexión sale de http.host y http.port en settings.json; el ejecutable los toma del config.json que tiene al lado.
  • El código del visor vive en workspace/web-launcher, fuera de este repositorio.

Códigos de estado

CódigoCuándo
200La operación se resolvió.
201Se creó el recurso.
400Entrada inválida: prioridad fuera de rango, motivo desconocido, campos que faltan.
404La referencia no corresponde a ninguna tarea ni etiqueta.

El cuerpo de un error es siempre {"error": "..."}, con el código que corresponde, y nunca un error dentro de una respuesta correcta. Cada petición de escritura contiene un único valor JSON: cualquier contenido posterior es entrada inválida y no modifica el proyecto. El estado del producto se consulta con una petición y responde la versión, la versión del esquema y el prefijo en uso:

curl -s http://127.0.0.1:8891/api/status
# {"version":"0.1.0","schema":6,"prefix":"tk"}

El canal de cambios

GET /api/events mantiene un canal abierto y emite un evento por aviso, en el orden en que ocurrieron. Cada evento lleva el nombre workspace.changed y el aviso en JSON: el recurso que cambió, sin decir quién lo pidió.

id: 11
event: workspace.changed
data: {"resource":"tasks","changes":[{"id":"tk-1","action":"actualizada","title":"Preparar el informe trimestral de ventas"}]}
id: 11
event: workspace.changed
data: {"resource":"tasks","changes":[{"id":"tk-1","action":"actualizada","title":"Prepare the quarterly report"}]}
  • changes nombra la tarea con su referencia, lo que le pasó —creada, cerrada o actualizada— y su título. El aviso de una etiqueta no lo lleva.
  • Quien lee continúa donde se quedó: la primera lectura pide ?after=<id> y al reconectar se retoma del aviso de la cabecera Last-Event-ID. Sin ninguna de las dos, el canal empieza por el cambio siguiente, así que abrir la pantalla no suelta el historial.
  • El aviso se lee de la base, no de la memoria del servidor: por eso un cambio pedido por la terminal llega al canal.
  • En el listado de la API, parent_id es el número interno del padre; la referencia visible la compone quien pinta, con el prefijo del proyecto.

Los agentes

Las dos integraciones con agentes —Pi y OpenCode— te dan el tablero del proyecto como herramientas. Están escritas en TypeScript y init las deja en .tasks-ai/extensions/pi/ y .tasks-ai/extensions/opencode/, para que el proyecto las cargue desde su propia carpeta, sin depender del repositorio de origen.

Las dos ejecutan el CLI del producto y devuelven su JSON. No tocan la base ni reimplementan reglas: lo que el producto rechaza, llega rechazado.

Las herramientas

La extensión de Pi

El paquete que dejó init se registra en el proyecto con la primera orden, y se retira con la segunda:

pi install -l .tasks-ai/extensions/pi              # registra la extensión instalada
pi remove -l --approve .tasks-ai/extensions/pi     # la retira y deja la configuración como estaba
pi install -l .tasks-ai/extensions/pi              # registers the installed extension
pi remove -l --approve .tasks-ai/extensions/pi     # removes it and leaves the configuration as it was

Con el paquete registrado, arranca Pi desde la raíz del proyecto: la extensión encuentra el tablero subiendo desde el directorio de trabajo, igual que el CLI, y ejecuta el binario instalado o, si falta, el del PATH.

En el TUI, /board muestra el tablero en la conversación: el mismo resumen que el agente recibe al empezar cada turno.

El tablero en cada turno

El agente recibe el tablero al empezar cada turno: contadores, la tarea en curso, unas pocas de las que se pueden empezar y las reglas de uso. Va en las instrucciones del turno, no como mensaje en la conversación.

Mientras la extensión está cargada y el proyecto tiene tablero, la herramienta todo del arnés no está disponible: el tablero es el único sitio donde se anota el trabajo. En un proyecto sin tablero, todo sigue disponible y el resumen lo dice. Al descargar la extensión, todo vuelve. El resumen y tasks_board comparten una sola lectura del tablero: si acabas de leerlo, no se vuelve a ejecutar el CLI; una escritura obliga a leer de nuevo.

El tablero mientras trabajas

Con la extensión cargada, el tablero está a la vista mientras trabajas: una línea de estado que empieza por 🦊 última cerrada: y nombra la última tarea cerrada —recortada a 100 caracteres— y, encima del editor, un bloque con el título 🦊 Tasks-ai tablero: y una línea por tarea en curso. Sin ninguna cerrada, la línea dice 🦊 tablero: sin tarea cerrada; sin nada en curso, el bloque lo dice; en un proyecto sin tablero el bloque se retira y la línea de estado avisa de que no hay tablero.

Los dos se repintan al empezar cada turno y después de cada escritura. La extensión no vigila la base: un cambio hecho desde otra terminal aparece en el turno siguiente o cuando el agente vuelve a leer el tablero, no en el acto.

La extensión de OpenCode

El proyecto la carga desde su opencode.jsonc:

{
  "plugins": ["./.tasks-ai/extensions/opencode"]
}
{
  "plugins": ["./.tasks-ai/extensions/opencode"]
}

Registra las mismas once herramientas y añade el resumen del tablero al sistema de cada petición; no tiene /board ni bloque del TUI, porque el plugin de servidor de OpenCode no los ofrece. El TODO del arnés no sustituye al tablero: la misión nombra su tk-N y el tablero sigue siendo la única fuente de tareas.

El contexto que recibe el agente

El tablero es una proyección: referencia, título, estado, bloqueo, prioridad, padre y etiquetas. No incluye descripciones, notas ni comentarios.

El árbol se recorta a 40 tareas, con un aviso de cuántas quedan fuera. Las listas de tareas en curso y de lo que puedes empezar se recortan a 8 cada una.

Cuando pides el detalle de una tarea, recibes su descripción entera y los 10 comentarios más recientes. Estos recortes son de las extensiones: el CLI sigue devolviendo todo.

Lo que no hace

Ninguna de las dos habla MCP, añade un comando ready ni un importador. No son una tercera superficie del producto: envuelven el CLI.

La configuración

Un archivo, cuatro claves, y la posibilidad de editarlo a mano. El producto lo escribe al instalar y no vuelve a tocarlo.

{
  "prefix": "tk",
  "db": "tasks.db",
  "http": { "host": "127.0.0.1", "port": 8890 },
  "log": { "level": "info" }
}
ClaveTipoPor omisiónQué hace
prefixtextotkEl prefijo de las referencias. Empieza por letra o número y sigue con letras, números, guiones o guiones bajos, hasta treinta y dos caracteres.
dbrutatasks.dbLa base, relativa a la carpeta del producto.
http.hosttexto127.0.0.1La dirección en la que escucha serve.

Cambiar el prefijo

El prefijo cambia lo que se escribe, no lo que se guarda: la base no se reescribe y las referencias del prefijo anterior dejan de resolver. El producto lo avisa al arrancar y sigue con el nuevo, así que el cambio se hace una vez y se deja. Fijarlo al instalar con init --prefix evita el cambio.

# settings.json con "prefix": "inf"
./tasks-ai create --title "Preparar el informe"      # devuelve "ref": "inf-6"
./tasks-ai show tk-1                                 # ya no resuelve: la tarea es inf-1
# settings.json with "prefix": "inf"
./tasks-ai create --title "Prepare the report"      # returns "ref": "inf-6"
./tasks-ai show tk-1                                # no longer resolves: the task is inf-1

Un valor inválido detiene el arranque con un mensaje claro, en lugar de arrancar con una configuración a medias. Es lo que quieres: un prefijo mal escrito cambiaría todas las referencias.

Lo que no hace

Tan importante como lo anterior: lo que el producto no promete, para no esperarlo.

No haceQué significa en la práctica
Borrar tareasNo hay orden de borrado. Una tarea se cierra con su motivo y se queda: el histórico del proyecto no se pierde.
Borrar comentariosNo hay orden de borrado. Si algo estaba mal, se corrige editando el cuerpo del comentario: su identidad y su fecha se quedan.
Guardar el estado «bloqueada»Se calcula en cada lectura desde las dependencias; no es un estado que se pueda poner ni quitar a mano.
Impedir ciclos de dependenciasSe permiten: A puede esperar a B y B a A. Si pasa, las dos aparecen bloqueadas y hay que retirar un bloqueo.
Cerrar en cascadaCerrar una subtarea no cierra al padre, y un padre con subtareas abiertas no se puede cerrar.
Interpretar la prioridadValida el rango y nada más: no ordena, no filtra por sí sola ni cambia el comportamiento de nada.
Tener usuarios ni permisosNo hay autenticación: el producto supone una persona en su máquina y escucha en 127.0.0.1 por omisión. Cambiar http.host expone la API a quien llegue a esa dirección, sin más protección. El servidor solo contesta a las peticiones dirigidas a su propio nombre y rechaza una escritura que el navegador marca como venida de otra página.
Sincronizar entre máquinasLa base es un archivo local. Ni se sincroniza ni se comparte sola, y dos procesos escribiendo sobre la misma base no es una forma de trabajo soportada.
Borrar un ADRNo hay orden de borrado. Un cambio de decisión se publica como un ADR nuevo que sustituye al anterior.
Versionar el proyectoNo sabe nada de Git ni de ramas: no registra commits, ni autores, ni estados de revisión.

La carpeta del producto es el producto. Copiar .tasks-ai/ a otro proyecto se lleva las tareas enteras; olvidarla al mover el proyecto se lleva la mitad de la historia.

Cuando la orden no llega a ejecutarse

Si el error no es JSON, el problema está antes del producto: el binario no se ejecuta. Un binario copiado sin permiso de ejecución responde EACCES desde la interfaz y Permission denied desde la terminal, y se arregla con un permiso, no con otra orden:

./tasks-ai list
# bash: ./tasks-ai: Permission denied          código 126

chmod +x tasks-ai                              # y vuelve a probar
./tasks-ai list
# bash: ./tasks-ai: Permission denied          code 126

chmod +x tasks-ai                              # then try again

Si la orden llega pero no encuentra el proyecto, es que no hay carpeta .tasks-ai/ en el camino: init la crea, y se ejecuta desde dentro del proyecto.

13

Preguntas cortas

Para quien llega con una duda concreta y no quiere releer la página entera.

¿Dónde están mis tareas?

En .tasks-ai/tasks.db, dentro del proyecto. No hay nada fuera de esa carpeta: si la copias, te llevas las tareas; si la borras, no hay nada que recuperar.

¿Puedo borrar una tarea?

No. Se cierra con un motivo —done, duplicate, absorbed, stale o superseded— y se queda en el listado. Se puede reabrir después.

¿Necesito Node o algo más para usar la interfaz?

No. La interfaz viaja dentro del binario: serve es lo único que hace falta. Node solo entra si trabajas en el código de la interfaz, no para usarla.

¿Por qué todo responde en JSON?

Porque la línea de órdenes y los agentes son consumidores de primera clase: un JSON se lee, se filtra y se encadena sin analizar texto pensado para ojos humanos. La interfaz web usa la API, que devuelve las mismas formas.

¿Puedo tener dos proyectos con el gestor?

Sí: cada proyecto tiene su propia carpeta .tasks-ai/ y su propia base. No se ven entre ellos y no hay un listado común.

¿Dos personas pueden trabajar a la vez?

No está pensado para eso. La base es un archivo local y no se sincroniza; dos procesos escribiendo sobre la misma base no es una forma de trabajo soportada.

¿Cómo sabe un agente que las tareas están aquí?

Porque el archivo de instrucciones del proyecto enlaza .tasks-ai/AGENTS.md. init devuelve la línea exacta en pointer; sin ella, el agente no tiene por qué enterarse.

¿Qué pasa si cambio el prefijo?

Que las referencias nuevas lo usan y las viejas dejan de resolver. La base no se reescribe: los números internos son los mismos, y el aviso al arrancar lo dice.

¿La prioridad 0 es la más alta?

El producto no lo decide: solo valida el rango de 0 a 3. La convención que uses es tuya, y conviene escribirla en las reglas del proyecto.

¿Puedo usar solo la API, sin la interfaz?

Sí. La API es la misma superficie que usa la interfaz. Lo que no hay es un modo sin serve: la API vive en ese proceso.
